# 提示词切片（AI 生成切片 SRT）

把一份**完整直播 SRT**按女装带货爆款结构重排成 46~60 秒的切片，再沿用原片时间戳去剪视频。

核心原则只有一句：**模型只负责挑哪几句，程序负责挑得对不对。**

## 流程图

```text
上传完整视频 + 完整 SRT
        │
        ▼
POST /api/jobs/{id}/hooks        生成 3~6 个候选开头钩子
        │
        ▼
用户在前端选一个钩子（也可跳过 AI，直接用原 SRT）
        │
        ▼
POST /api/jobs/{id}/clip-srt     按「五步结构」重排，写出 clip.srt 并自动规划切点
        │
        ▼
现有剪辑流程：plan → start → merged.mp4 + clips/
```

## 提示词

两个模板放在 `backend/app/prompts/`：

- `hooks.md`：只挑开头。优先级为 价格锚/价格乌龙 > 痛点/极端场景 > 结果反差 > 主理人故事；
  禁止「这是一件 XX」式开场，禁止单独讲成分工艺（除非原话自带价格或结果）。
- `clip.md`：五步结构（给需求 → 给价值 → 给福利 → 给信任 → 给稀缺），
  12~18 段，总时长 46~60 秒，越接近 58 秒越好；数组顺序就是成片播放顺序。

两个模板都强调：**只能选连续相邻条目，不能改写一个字。**

## 穿搭场景与高光片段（有则选，不硬套）

- **穿搭场景**：字幕里提到了适用场合/搭配方式（上班通勤、约会、逛街、居家、聚会、送礼、内搭外穿、叠穿、配什么）时，会选进成片（step=`场景`）；字幕里没有就不选、不编造。
- **展示高光**：字幕里有“转一圈/看整体/上身效果/这样搭一套”等展示动作时，尽量选入成片（step=`展示`）并多放进候选库。
- **赞美高光**：字幕里有“太漂亮/好看/绝了/高级感/显瘦/谁穿谁好看”等夸赞时，尽量选入成片（step=`赞美`）；“赞美 + 展示”紧挨出现时优先作为完整高光保存。
- **实穿优点（重要）**：字幕里的体感/实用性表述都算价值点，不能当闲聊跳过——“而且非常轻”“这件非常的非常的轻”“很保暖”“柔软/绵密”“不易皱/不起坨/不起球/不掉毛”“垂坠/显高/百搭/不过时”。挑 1~2 段进成片价值段，且至少留一段进候选库；“轻 + 保暖”同时出现时尤其要保住（羊毛大衣能轻是强卖点）。程序侧有软提示兜底：“轻/保暖/柔软”等线索出现却没被选入时提醒一次。“轻”用正则单独判定，不会把“年轻”误判成“轻”。
- **尺码片段（必须要有）**：字幕里只要出现尺码信息（尺码/码数/卡码/拍大/拍小/正常拍/能穿到/多少斤），成片就**必须**含一段尺码，否则程序判定不合格、带着原因让模型重选（最多 3 次，一直不给就报错，不会悄悄生成没有尺码的成片）。优先选**完整尺码表**（如“105 115 125 能穿到 140 斤”），其次是**卡码建议**（“卡码正常拍/卡码拍大/个子高不用拍大一码”）；位置要求放在结尾前 2~3 段，紧跟福利、稀缺之前。字幕里完全没有尺码信息时不校验、不编造。
- **价格感叹（低优先级）**：字幕里有“好便宜/性价比太高/划算/太值了”等感叹价格的短句，属弱高光；成片时长允许时可顺进一段，但不为此挤出更有价值的内容，且一律放进候选库保留。
- **候选库一次性扫全**：候选库 spare 与成片在同一次模型调用中产出（不通读两次），提示词要求模型**通读全篇（含片尾）**按五类逐条扫，**数量由内容决定、符合要求的全部保留、不预设上限也不凑数**；程序侧再做成片重叠去重保护。
- **不硬套**：以上只依据字幕文字判断（模型看不到画面），字幕里没有的就不会凭空生成；程序侧只会给“建议补充”的软提示，不会阻断。

## 硬校验（程序兜底）

模型输出后逐条校验，不合格会自动带着原因重试（切片最多 3 次）：

- 每条片段 = 原 SRT 的连续区间 `[a, b]`，文本由原句直接拼接；
- 时间戳 = 首条 `start` → 末条 `end`，不重建、不从 00:00:00 起排；
- 同一画面不能重复使用（区间重叠直接判不合格）；
- 单条片段不超过 12 秒；
- 总时长硬边界 40~72 秒，推荐区间 46~60 秒（超出推荐值只警告）；
- 所选开头钩子必须出现在成片里，且被强制放到第一条；
- 字幕里有尺码信息时，成片必须有尺码段或完整尺码表，否则重试；
- 区间内条目在原片时间上必须向前（乱序区间会被拒绝）。

最终成片 SRT 的条目顺序可以跨时间点重排，因此**时间戳不递增是正常的**。

## 模型配置

优先读项目根目录的 `.env`（已在 `.gitignore` 中忽略），也支持同名环境变量：

```bash
LLM_PROVIDER=openai            # openai 或 ollama，默认按是否配置 key 自动判断
LLM_BASE_URL=https://xxx/v1    # OpenAI 兼容地址（通常以 /v1 结尾）
LLM_API_KEY=sk-xxx
LLM_MODEL=deepseek-chat
LLM_TIMEOUT=180                # 单次请求超时（秒）；流式下是“两块数据间的最长等待”
LLM_TEMPERATURE=0.2
LLM_STREAM=on                  # 默认开：流式请求，避网关 524；服务不支持时自动回退非流式
```

### 为什么要流式（网关 524 的真相）

很多 OpenAI 兼容中转站（如 `loxo.cc`）前面挂的是 Cloudflare。它的规则是：
**上游连续约 100 秒不吐出任何数据，就直接强行返回 524 + 一张 HTML 错误页。**
所以：

- `LLM_TIMEOUT` 调得再大也没用——先被网关掐断了；
- 重试也没用——同样的输出量还会再次超时；
- 以前只挑 12~18 段成片，几十秒就吐完了；现在候选库要**一次通读全篇，有多少符合条件的就留多少**，输出量翻倍，很容易超过 100 秒。

解决办法是**让请求持续吐数据**：`llm.py` 默认用流式（`stream: true`）逐块接收并拼接，
网关每收到一点数据就重置计时，不会判超时。实测同一份 775 条字幕：
非流式 118~127 秒（时不时 524），流式首包 3 秒、完整 166 秒且稳定成功。

如果中转服务不支持 `stream`，程序会自动回退到普通非流式请求（也就是老行为）。
出现 524 时上层会给出中文提示，不再把整页 HTML 抛给用户。

不配置任何 key 时，会尝试本机 Ollama（`127.0.0.1:11434`），并自动挑选第一个非向量模型。
想用本地模型，推荐先 `ollama pull qwen2.5:7b`，再设置 `LLM_MODEL=qwen2.5:7b`。

`GET /api/llm` 返回当前配置摘要（不含密钥），前端右上角会显示模型名。

## 接口

### POST /api/jobs/{id}/hooks

```json
{ "count": 4, "force": false }
```

返回任务快照，新增字段：

```json
{
  "hooks": [
    {
      "id": "h1", "type": "价格乌龙", "a": 130, "b": 132,
      "start": 172.766, "end": 178.5, "duration": 5.734,
      "text": "……", "reason": "……"
    }
  ],
  "hook_warnings": [],
  "generation": { "status": "hooks_ready", "error": null }
}
```

### POST /api/jobs/{id}/clip-srt

```json
{ "hook_id": "h1" }
```

返回快照，新增 `clip_srt`：

```json
{
  "path": "clip.srt",
  "count": 14,
  "duration": 59.54,
  "memory_point": "加绒加厚也不显胖",
  "warnings": [],
  "segments": [
    { "a": 130, "b": 132, "step": "钩子", "duration": 5.734, "text": "……" }
  ]
}
```

同时自动执行一次 `plan`，前端可直接看到切点表。

返回体中还包含：

- `library`：候选片段库，每项带唯一 `id`（`s*` 为成片段，`c*` 为备用候选段）；
- `composition`：当前成片的片段 `id` 顺序。

### POST /api/jobs/{id}/composition

```json
{ "segment_ids": ["s1", "c1", "s2"] }
```

按给定的片段 `id` 顺序重建成片，并自动重新 `plan`。可用于替换、排序、删除、追加片段：

- 替换：用候选 `id` 替换某个成片 `id`；
- 排序：调整 `id` 在数组中的位置；
- 删除：从数组移除某个 `id`；
- 追加：在数组末尾插入候选 `id`。

返回快照，`plan.items` 顺序与 `composition` 一致。

### POST /api/jobs/{id}/reset-clip

放弃切片，恢复上传的完整 SRT，并清掉 `clip.srt` 与旧成片。

## 产物

```text
data/jobs/<任务ID>/
├── clip.srt      # 切片字幕（时间戳来自原片，可直接对照原视频剪）
├── hooks.json    # 候选钩子 + 模型信息 + 警告，便于复盘
└── plan.json     # 切片后的逐段切点
```

## 常见问题

- **提示「无法连接本地 Ollama」**：先 `ollama serve`，或在 `.env` 配 `LLM_BASE_URL / LLM_API_KEY / LLM_MODEL`。
- **提示「模型没有返回合法 JSON」**：换更强的模型，或把 `LLM_TEMPERATURE` 调到 0。
- **总时长不合格**：模型没算准时长，会自动重试；连续失败可减少输入字幕条数
  （先把直播按商品切开、只上传目标商品那一段）。
- **等待时间长**：一次切片生成通常 30~120 秒，页面会显示进度提示，属于正常现象。
